# Проверяемое сравнение ресурсов

`Measure-Client.ps1` работает в Windows PowerShell 5.1 и PowerShell 7 без запуска от администратора. Он измеряет корневой процесс и наблюдаемое дерево его потомков. Скрипт не читает профили, cookies, токены, командные строки и заголовки окон. Результат содержит путь к EXE, PID, времена создания процессов и сведения о среде. Доступа к учётной записи Яндекса ему не требуется.

Скрипт сам не определяет, какой клиент быстрее или легче. Готового сравнительного результата здесь нет. Официальный клиент для проверки скрипта не запускался.

## Два режима

Предпочтительный режим для памяти и CPU — подключение к уже работающему корневому процессу. Откройте клиент, войдите, дождитесь загрузки избранного и получите его корневой PID в диспетчере задач. Передайте PID основного EXE, а не случайного renderer-процесса:

```powershell
& '.\tools\Measure-Client.ps1' -RootProcessId 12345 -WarmupSeconds 10 -DurationSeconds 30 -ResultsDirectory '.\results\native-visible-run1'
```

Запуск по точному пути к EXE дополнительно измеряет время до первого наблюдаемого главного окна:

```powershell
& '.\tools\Measure-Client.ps1' -ExecutablePath '.\app\YMusic.Native.exe' -WarmupSeconds 10 -DurationSeconds 30 -ResultsDirectory '.\results\native-startup-run1'

& '.\tools\Measure-Client.ps1' -ExecutablePath 'C:\Users\senduora\AppData\Local\Programs\YandexMusic\Яндекс Музыка.exe' -WarmupSeconds 10 -DurationSeconds 30 -ResultsDirectory '.\results\official-startup-run1'
```

Команды предполагают папку исходников Yamuse. В официальном клиенте ранее обнаружена версия `5.124.1.r21717235`; каждый запуск записывает свежую версию и SHA256 фактически выбранного EXE. Хеш EXE не является хешем всего приложения: ресурсы и DLL могут изменяться отдельно.

Перед запуском скрипт проверяет процессы с тем же именем и точным путём. Если цель уже работает, он выдаёт PID и требует режим `-RootProcessId`, не создавая второй экземпляр. Если путь одноимённого процесса недоступен, запуск также отменяется. Это предварительная проверка, а не системная блокировка: не запускайте вторую копию вручную одновременно со скриптом.

Приложение, запущенное скриптом, остаётся открытым. Уже работающие процессы также не завершаются. Окно, состояние плеера, вход и сворачивание скрипт не переключает. Аргументы запуска EXE не передаются. Не меняйте политику безопасности или права системы ради замера; при запрете доступа используйте процесс своего пользователя либо сохраните ошибку как ограничение.

## Что именно измерено

| Поле | Значение и пределы |
| --- | --- |
| `WorkingSetBytesSum` | Сумма рабочих наборов процессов: страницы, находящиеся в RAM. Общие страницы могут учитываться несколько раз, поэтому это **не уникальная физическая память дерева**. |
| `PrivateBytesSum` | Сумма private committed bytes, в том числе страниц вне RAM. Это **не размер резидентной памяти**. |
| `CpuPercentNormalized` | `100 × CPU миллисекунды за интервал / (фактический интервал × 1000 × логические процессоры машины)`. Полная загрузка одного ядра на машине с 16 логическими процессорами — около 6,25%. |
| `ProcessCount` | Число живых доступных процессов дерева в данном наблюдении. В JSON также есть количество уникальных наблюдавшихся процессов за окно замера. |
| `FirstObservedMainWindowMilliseconds` | Только режим запуска: время от вызова запуска до первого обнаруженного ненулевого `MainWindowHandle` в дереве. Это **proxy**, возможен splash. Это не время входа, загрузки коллекции или готовности воспроизведения. В attach-режиме значение `null`. |

По умолчанию прогрев занимает не менее 10 секунд, сбор — не менее 30 секунд, интервал — 1 секунду. Прогрев запускается после проверки окна либо истечения `MainWindowTimeoutSeconds` (по умолчанию 30 секунд); в attach-режиме — после подключения. Ожидание окна не входит в прогрев. Увеличивайте `WarmupSeconds` и `DurationSeconds`, если сценарий требует большего окна. Фактические времена и интервалы сохраняются: опрос сам требует некоторого времени, ровно 1000 мс не гарантируются.

Окно проверяется приблизительно каждые 100 мс плюс время снимка дерева; эта задержка входит в proxy запуска. Чтение SHA256 до запуска может прогреть файловый кеш EXE. Поэтому данный скрипт не устанавливает время истинного холодного запуска с диска.

Рабочий набор и private bytes в JSON имеют среднее по снимкам и максимальный **наблюдавшийся** снимок. Средний CPU рассчитывается по суммарному наблюдавшемуся времени CPU и фактической длительности, а не усреднением процентов с разными интервалами. CSV содержит каждый снимок в байтах и миллисекундах без округления до MB. Для MiB делите байты на `1048576`.

PID сопоставляется со временем создания процесса; повторное использование номера не присоединяет посторонний процесс. Новые потомки добавляются, известные потомки продолжают учитываться после выхода родителя. Для открытых процессов сохраняются OS handles, что позволяет учесть окончательное время CPU после их выхода. Handle закрывается после замера, сам процесс не завершается.

Опрос не атомарен. Очень короткий процесс вместе с ненаблюдавшимися предками может полностью пройти между снимками; его нагрузка будет пропущена. Короткие пики памяти также могут быть пропущены. Дочерний процесс, существовавший до начала сбора и замеченный позже, получает базу CPU при первом наблюдении: прежнее время не приписывается текущему интервалу. Независимые службы, внешние проигрыватели и отдельно запущенные экземпляры вне дерева не учитываются. Для полной системной трассировки нужен отдельный ETW/WPR-анализ.

В JSON сохраняются версия ОС, модель CPU, число логических процессоров, объём физической RAM, версия PowerShell и runtime самого измерителя. Runtime измерителя не выдаётся за runtime клиента. Сведения об имени компьютера и пользователе отдельно не собираются; имя пользователя может присутствовать в явно выбранном пути EXE.

## Честный протокол сравнения

1. Используйте одну машину, один план электропитания и одинаковые фоновые условия. Запускайте клиенты **по очереди**. Во время замера второго клиент из первого замера должен быть закрыт пользователем; скрипт его не закрывает.
2. В обоих клиентах войдите в одну учётную запись и дождитесь полной загрузки избранного. Сопоставьте число загруженных записей; если прототип загрузил только часть, сравнение полной коллекции некорректно. Прогрев не заменяет готовность данных.
3. Выделите отдельные сценарии: загруженное избранное без воспроизведения; воспроизведение одного и того же трека; тот же режим со свёрнутым окном. Сравнивайте свёрнутый клиент со свёрнутым. Состояние окна фиксируйте вручную до подключения скрипта.
4. Для воспроизведения выберите **один трек и одинаковое качество**, громкость, состояние повторения и доступ к сети/кешу. Не сравнивайте сетевую загрузку одного клиента с уже кешированным треком другого. Если качество или условия кеша не удаётся выровнять, прямо укажите это ограничение. Учитывайте буферизацию и позицию: используйте сопоставимый участок, не включайте границу трека в один из замеров случайно.
5. Используйте одинаковые `WarmupSeconds`, `DurationSeconds` и состояние окна. Выполните **не менее трёх повторов каждого клиента в каждом сценарии**, чередуя порядок (например, A–B, B–A, A–B). Не объединяйте первый холодный запуск с повторными тёплыми запусками в одну группу.
6. Сохраняйте результаты в отдельные папки с понятным сценарием и номером повтора. Рядом фиксируйте вручную трек, качество, кеш/сеть, полноту избранного, состояние окна, дату и версию пакета прототипа. Токены и пароли в эти записи не добавляйте.
7. Перед выводами проверяйте `CompletedRequestedWindow = true`, `TestOnly = false`, `ObservationComplete = true`, `ExecutableUnchanged = true` и отсутствие `Error`. При ошибке во время замера скрипт сохраняет частичные CSV/JSON и возвращает ошибку; такой запуск не используйте как полный повтор. Пропуски чтения не скрываются: смотрите счётчики в `Measurement`.
8. Сравнивайте медианы по повторам и разброс, отдельно для памяти, CPU, числа процессов и proxy запуска. Один удачный прогон не доказывает преимущество. Меньше процессов само по себе не означает меньше ресурсов; меньше private bytes не означает меньше физической RAM. До завершения такого протокола утверждение «быстрее/легче официального» остаётся непроверенным.

Для реального времени загрузки избранного или начала слышимого звука нужны отдельные определённые события/измерения. Метрика окна этого не доказывает.

`ObservationComplete` означает отсутствие известных отказов чтения, а не гарантию наблюдения каждого короткого процесса. Ограничения опроса сохраняются даже при значении `true`.

## Файлы результата и техническая проверка

Если `ResultsDirectory` не указан, используется `./results` относительно текущей папки. Каждый запуск создаёт уникальную пару `*.summary.json` и `*.samples.csv` в UTF-8 без BOM. Числа в CSV используют точку как десятичный разделитель независимо от языка Windows; разделитель колонок — запятая, поля заключены в кавычки. Сам `.ps1` сохранён в UTF-8 с BOM для чтения русских строк в Windows PowerShell 5.1. Никаких итоговых файлов поверх предыдущего запуска не записывается.

Для короткой проверки только самого измерителя разрешён `-TestMode -WarmupSeconds 2 -DurationSeconds 2`. В JSON такой запуск имеет `TestOnly = true`; он не подходит для вывода о ресурсах клиентов. Используйте отдельный безвредный процесс своего пользователя. Синтаксис можно проверить без запуска приложения:

```powershell
$parseTokens = $null
$parseErrors = $null
[System.Management.Automation.Language.Parser]::ParseFile((Resolve-Path '.\tools\Measure-Client.ps1'), [ref]$parseTokens, [ref]$parseErrors) | Out-Null
if ($parseErrors.Count) { $parseErrors; throw 'Ошибка синтаксиса' }
```

В среде проверки парсер прошёл в PowerShell 5.1.26100.9711 и 7.6.5. Короткий функциональный тест выполнен в PowerShell 7 на отдельно созданном PowerShell-процессе с потомком. В Windows PowerShell 5.1 локальная политика запрещала запуск `.ps1`; она не менялась, поэтому функциональное выполнение именно в 5.1 не подтверждено. При таком ограничении сохраните его в отчёте и используйте разрешённую среду PowerShell 7.
